# Domain-to-deploy loop

This guide explains how a project generated by Anti-Gravital becomes reachable
through a custom domain, and which parts of that loop are real today. It is a
practical companion to the domain control plane (`ag-domains`) and the edge
data plane (`ag-edge`) described in RFC-0011 / ADR-0012.

## Status of this guide

Be precise about what exists:

- **Implemented and usable now**: attaching a domain, printing DNS records,
  exporting a BIND zone, ownership verification, status/listing, diagnostics
  and detaching. These are the `ag domains` commands listed below and are
  present in the alpha binary.
- **In progress in wave 8 (planned, not yet in this checkout)**: the
  `ag dns plan|apply|status` surface, a single-command project-to-URL link,
  and the concrete environment/visibility configuration keys. They are
  described here as the target design so the flow is understandable, but do
  not rely on them until they ship. See "Commands" and the notes handed to the
  coordinator.

No live DNS provider, registrar account or cluster is required to follow the
local part of the loop (CLAUDE.md rule 12, ADR-0009).

## What the loop does

```text
schema.ag / ag new            -> generated project (local service via ag dev)
        |
        v
optional deploy artifacts     -> Docker Compose / Kubernetes (wave 7, opt-in)
        |
        v
ag domains attach             -> local attachment + exact DNS records to publish
        |
        v
provider DNS + TXT proof       -> ag domains verify / diagnose
        |
        v
HTTPS at the hostname         -> ACME issuance (HTTP-01 or DNS-01 for wildcards)
        |
        v
reachable service             -> edge routes the hostname to the target
```

The control plane owns state and decisions (attachment lifecycle, ownership,
DNS instructions, CAA preflight, diagnostics). The data plane resolves the
incoming hostname, selects the certificate by SNI and applies the
canonical/redirect policy. Anti-Gravital does not buy, transfer or renew
domains, and does not replace Terraform or Kubernetes.

## Prerequisites

| Requirement | Minimum | Check |
| --- | --- | --- |
| Rust toolchain | 1.99.1 | `rustc --version` |
| `ag` binary | alpha `0.1.0-alpha.1` or newer source build | `ag --version` |
| A domain you control | any registrar | DNS dashboard access |
| Edge target | hostname (CNAME) or apex IPs (A/AAAA) | from your hosting setup |

Provider credentials are **optional**: the manual attachment flow writes a
local JSON store and prints the records for you to paste. Only `ag domains
sync` (SPF/DKIM/DMARC) and credentialed ACME automation need a provider token.

## The three environments

Use a separate hostname and a separate attachment per environment. The
conceptual model is:

| Environment | Purpose | Typical hostname | Visibility |
| --- | --- | --- | --- |
| `dev` | local iteration on `ag dev`; loopback or a hosts-file entry | `api.dev.example.com` | private |
| `staging` | shared preview for the team before release | `staging.example.com` | private / restricted |
| `prod` (`production`) | the public service | `example.com`, `api.example.com` | public |

`local` is a fourth, loopback-only case: no DNS records, no TLS and no
manifest entry; use `ag dev` directly.

Notes on naming and configuration:

- `ag domains attach` currently accepts `--env <E>` with a default of
  `production` and `--service <S>` with a default of `default`. The CLI does
  not yet enforce a fixed environment vocabulary.
- The planned canonical IDs are `dev`, `staging` and `production`, with `prod`
  as an alias for `production`. Visibility defaults to private (fail-closed).
- The concrete keys for environment and visibility (`ag.toml` and
  `config/<env>.toml`) are being defined by the wave-8 environment model.
  Record the `--env` value you used in the attachment so the mapping stays
  explicit.

## Point a custom domain at a deployed service

The deployed service only needs to be reachable at the edge target you
declare. The domain layer binds a hostname to that target; it does not deploy
the service for you.

1. Have a service running (locally with `ag dev`, or through the optional
   wave-7 Docker/Kubernetes artifacts).
2. Attach the hostname, declaring project, environment, service and target:

   ```bash
   ag domains attach api.example.com \
     --project my-api --env production --service default \
     --edge-host edge.example.net
   ```

   For an apex domain use `--ip <IPv4>` / `--ip <IPv6>` instead of a CNAME.
3. Publish exactly the printed records at your DNS provider: the `TXT
   _ag-domain.<registrable-domain>` ownership record and the routing record
   (`CNAME` for a subdomain, `A`/`AAAA` for an apex, `CNAME *` for a
   wildcard). `ag domains instructions` reprints them;
   `ag domains export-zone` produces a BIND fragment.
4. Prove ownership:

   ```bash
   ag domains verify api.example.com
   ag domains status api.example.com
   ```

   Repeat `verify` after propagation if it still reports pending.
5. Confirm the DNS side agrees with the attachment:

   ```bash
   ag domains diagnose api.example.com --edge-host edge.example.net
   ```

   "No action required" means the records match.
6. Terminate TLS at the hostname (ACME HTTP-01 for exact names, DNS-01 for
   wildcards) and route the request to the service. Keep the certificate and
   routing wiring under your deployment's control; the alpha documents the
   library-level listeners, not a managed hosted edge.

Repeat the flow with a different hostname and `--env` value for staging and
dev. Detach with `ag domains detach <domain>` when a hostname is retired;
remember to remove the records at the provider as well.

## Public vs private

- **Public** (`prod`): the hostname resolves in public DNS, ownership is
  verified, a public CA certificate is issued, and the service is reachable
  from the Internet. Use a separate attachment per hostname.
- **Private** (`dev`, `staging`): keep the hostname off public resolution.
  Use loopback or a hosts-file entry locally, or an internal DNS zone for a
  shared staging host. Do not publish a TXT ownership proof or request a
  publicly trusted certificate for a name you intend to keep internal;
  use an internal CA instead.
- **Restricted** (`vpn-only`, planned): a private hostname behind a CIDR
  allowlist, with TLS but no public DNS exposure.
- A hostname that is not attached to any known target fails closed at the
  edge. Legacy default routes are the only fail-open case (RFC-0011).

Note: the implemented `ag domains attach` always prints a TXT ownership
record. For a private hostname, do not publish that record and do not expect
`ag domains verify` to confirm it through public resolvers; the planned
private path uses a link or a local hosts entry instead.

The exact visibility keys are part of the planned environment model. Until
they land, visibility is an operator decision expressed by what you publish
in DNS, not something the alpha CLI enforces.

## Troubleshooting

### Propagation

`ag domains verify` stays pending, or `diagnose` reports a record missing
right after you added it. Low TTLs help. Re-run after a few minutes. Confirm
the exact ownership value at the registered domain with
`ag domains check --domain _ag-domain.<registered-domain> --expected <value>`.

### Ownership verification

The ownership TXT record always lives at the registrable domain, so one proof
covers the apex and its subdomains. If `diagnose` reports "wrong value", an old
hosting record is usually still present; replace it at your provider. A name
cannot have both a CNAME and A/AAAA records: remove one.

### Wildcard

Attach `*.example.com` and publish `CNAME * -> <edge-host>`. Certificate
issuance for a wildcard requires a DNS-01 challenge: a `_acme-challenge.<base>`
TXT record. The manual flow asks you to add it when prompted; a provider
adapter creates and removes it automatically.

### TLS / certificate issuance

If ownership and DNS are correct but no certificate is issued:

- CAA: records that exclude the configured CA block issuance. The control
  plane runs a CAA preflight; allow the CA in your DNS.
- HTTP-01: the hostname must resolve to the edge and be reachable on port 80
  so the CA can fetch `/.well-known/acme-challenge/<token>`. Disable a proxy
  in front of the host for the first issuance if needed.
- Rate limits: issuance deduplicates by SAN set and counts per registered
  domain. Wait for the CA window to reset rather than retrying in a loop.

### Detach and takeover

`ag domains detach <domain>` writes a tombstone (default 30 days) that blocks
re-attaching the hostname. Wait for it to expire, or use another host;
reactivation requires a fresh ownership proof.

## Security notes

- Never commit provider tokens, zone IDs or passwords. Keep them in
  environment variables (`AG_CLOUDFLARE_TOKEN`, `AG_DNS_ZONE_ID`) or in an
  untracked `.env` file, which `.gitignore` already excludes.
- Use placeholder-only examples (`.env.example`) in templates and docs.
- The ownership TXT value is public by design; the local state file
  (`.ag/domains.json`) is environment state, not a secret store. Do not put
  credentials in it, and keep it out of version control if it carries
  environment-specific data.
- Prefer the native flow: `attach`, `verify`, `diagnose` and `detach` need no
  credentials. Provider automation stays behind an opt-in Cargo feature.
- Keep private hostnames private: no public TXT proof, no public CA
  certificate, no public DNS record.
- Do not treat a wildcard binding as a security boundary: a label-boundary
  defect in SNI/route matching is under audit in wave 8. Prefer exact
  hostnames until it is fixed.
- Detach tombstones prevent subdomain takeover; do not shorten the default
  without a documented reason.

# Circulo dominio-despliegue

Esta guia explica como un proyecto generado por Anti-Gravital se vuelve
alcanzable mediante un dominio propio y que partes del circulo existen hoy.
Es un complemento practico del plano de control (`ag-domains`) y del plano de
datos (`ag-edge`) descritos en RFC-0011 / ADR-0012.

## Estado de esta guia

Hay que ser preciso sobre lo que existe:

- **Implementado y usable ahora**: adjuntar un dominio, imprimir los registros
  DNS, exportar una zona BIND, verificar la propiedad, estado y listado,
  diagnosticos y desadjuntar. Son los comandos `ag domains` enumerados abajo
  y estan presentes en el binario alpha.
- **En curso en la ola 8 (planificado, aun no en este checkout)**: la interfaz
  `ag dns plan|apply|status`, un enlace unico de proyecto a URL y las claves
  concretas de configuracion de entorno y visibilidad. Se describen como
  diseno objetivo para que el flujo sea comprensible, pero no dependas de
  ellos hasta que se publiquen. Consulta "Comandos" y las notas entregadas al
  coordinador.

No se necesita un proveedor DNS real, una cuenta de registrador ni un cluster
para seguir la parte local del circulo (regla 12 de CLAUDE.md, ADR-0009).

## Que hace el circulo

```text
schema.ag / ag new            -> proyecto generado (servicio local con ag dev)
        |
        v
artefactos de despliegue      -> Docker Compose / Kubernetes (ola 7, opcional)
        |
        v
ag domains attach             -> adjunto local + registros DNS exactos a publicar
        |
        v
DNS del proveedor + prueba TXT -> ag domains verify / diagnose
        |
        v
HTTPS en el hostname          -> emision ACME (HTTP-01 o DNS-01 para comodines)
        |
        v
servicio alcanzable           -> el edge enruta el hostname al destino
```

El plano de control posee el estado y las decisiones (ciclo de adjunto,
propiedad, instrucciones DNS, preflight CAA, diagnosticos). El plano de datos
resuelve el hostname entrante, selecciona el certificado por SNI y aplica la
politica canonica/redirect. Anti-Gravital no compra, transfiere ni renueva
dominios, y no reemplaza Terraform ni Kubernetes.

## Requisitos previos

| Requisito | Minimo | Verificacion |
| --- | --- | --- |
| Toolchain Rust | 1.99.1 | `rustc --version` |
| Binario `ag` | alpha `0.1.0-alpha.1` o build posterior desde fuente | `ag --version` |
| Un dominio que controles | cualquier registrador | acceso al panel DNS |
| Destino edge | hostname (CNAME) o IPs del apex (A/AAAA) | segun tu hosting |

Las credenciales del proveedor son **opcionales**: el flujo manual de adjunto
escribe un almacen JSON local e imprime los registros para que los pegues.
Solo `ag domains sync` (SPF/DKIM/DMARC) y la automatizacion ACME con
credenciales requieren un token de proveedor.

| `staging` | vista previa compartida antes del release | `staging.example.com` | privado / restringido |
| `prod` (`production`) | servicio publico | `example.com`, `api.example.com` | publico |

`local` es un cuarto caso, solo loopback: sin registros DNS, sin TLS y sin

## Senalar un dominio propio a un servicio desplegado

El servicio desplegado solo necesita ser alcanzable en el destino edge que
declares. La capa de dominio enlaza un hostname con ese destino; no despliega
el servicio por ti.

1. Ten un servicio en ejecucion (localmente con `ag dev`, o mediante los
   artefactos opcionales Docker/Kubernetes de la ola 7).
2. Adjunta el hostname declarando proyecto, entorno, servicio y destino:

   ```bash
   ag domains attach api.example.com \
     --project my-api --env production --service default \
     --edge-host edge.example.net
   ```

   Para un dominio apex usa `--ip <IPv4>` / `--ip <IPv6>` en vez de un CNAME.
3. Publica exactamente los registros impresos en tu proveedor DNS: el TXT
   `_ag-domain.<dominio-registrable>` de propiedad y el registro de enrutado
   (`CNAME` para subdominio, `A`/`AAAA` para apex, `CNAME *` para comodin).
   `ag domains instructions` los reimprime; `ag domains export-zone`
   produce un fragmento BIND.
4. Prueba la propiedad:

   ```bash
   ag domains verify api.example.com
   ag domains status api.example.com
   ```

   Repite `verify` tras la propagacion si sigue pendiente.
5. Confirma que el DNS coincide con el adjunto:

   ```bash
   ag domains diagnose api.example.com --edge-host edge.example.net
   ```

   "No action required" significa que los registros coinciden.
6. Termina TLS en el hostname (ACME HTTP-01 para nombres exactos, DNS-01 para
   comodines) y enruta la peticion al servicio. Manten el certificado y el
   enrutado bajo el control de tu despliegue; el alpha documenta los
   listeners a nivel de libreria, no un edge hospedado y gestionado.

Repite el flujo con otro hostname y otro valor de `--env` para staging y dev.
Desadjunta con `ag domains detach <domain>` cuando retires un hostname;
recuerda quitar tambien los registros en el proveedor.

## Publico vs privado

- **Publico** (`prod`): el hostname resuelve en DNS publico, se verifica la
  propiedad, se emite un certificado de una CA publica y el servicio es
  alcanzable desde Internet. Usa un adjunto distinto por hostname.
- **Privado** (`dev`, `staging`): manten el hostname fuera de la resolucion
  publica. Usa loopback o una entrada en hosts localmente, o una zona DNS
  interna para un host staging compartido. No publiques una prueba TXT de
  propiedad ni pidas un certificado publico de confianza para un nombre que
  quieras mantener interno; usa una CA interna.
- **Restringido** (`vpn-only`, planificado): un hostname privado detras de una
  lista de CIDR permitidos, con TLS pero sin exposicion DNS publica.
- Un hostname no adjuntado a ningun destino conocido falla cerrado en el
  edge. Las rutas por defecto heredadas son el unico caso que falla abierto
  (RFC-0011).

Nota: `ag domains attach`, tal como esta implementado, siempre imprime un
registro TXT de propiedad. Para un hostname privado, no publiques ese
registro y no esperes que `ag domains verify` lo confirme mediante
resolvers publicos; el camino privado planificado usa un enlace o una
entrada local en hosts.

Las claves exactas de visibilidad forman parte del modelo de entornos
planificado. Hasta que lleguen, la visibilidad es una decision del operador
expresada en lo que publicas en DNS, no algo que la CLI alpha imponga.

## Resolucion de problemas

### Propagacion

`ag domains verify` sigue pendiente, o `diagnose` indica que falta un registro
justo despues de anadirlo. Los TTL bajos ayudan. Repite tras unos minutos.
Confirma el valor exacto de propiedad en el dominio registrado con
`ag domains check --domain _ag-domain.<dominio-registrado> --expected <valor>`.

### Verificacion de propiedad

El TXT de propiedad vive siempre en el dominio registrable, asi que una sola
prueba cubre el apex y sus subdominios. Si `diagnose` dice "wrong value",
normalmente queda un registro antiguo de otro hosting; reemplazalo en el
proveedor. Un nombre no puede tener a la vez CNAME y A/AAAA: elimina uno.

### Comodin

Adjunta `*.example.com` y publica `CNAME * -> <edge-host>`. La emision de
certificado para un comodin requiere un desafio DNS-01: un TXT
`_acme-challenge.<base>`. El flujo manual te pide anadirlo cuando corresponde;
un adaptador de proveedor lo crea y lo elimina automaticamente.

### TLS / emision de certificado

Si la propiedad y el DNS son correctos pero no se emite certificado:

- CAA: unos registros que excluyen la CA configurada bloquean la emision. El
  plano de control ejecuta un preflight CAA; permite la CA en tu DNS.
- HTTP-01: el hostname debe resolver al edge y ser alcanzable en el puerto 80
  para que la CA obtenga `/.well-known/acme-challenge/<token>`. Desactiva un
  proxy delante del host para la primera emision si hace falta.
- Limites de tasa: la emision deduplica por conjunto SAN y cuenta por
  dominio registrado. Espera a que se reinicie la ventana de la CA en vez de
  reintentar en bucle.

### Desadjuntar y takeover

`ag domains detach <domain>` escribe un tumba (30 dias por defecto) que
impide volver a adjuntar el hostname. Espera a que caduque o usa otro host;
la reactivacion requiere una prueba de propiedad nueva.

## Notas de seguridad

- Nunca commitees tokens de proveedor, IDs de zona ni contrasenias. Guardalos
  en variables de entorno (`AG_CLOUDFLARE_TOKEN`, `AG_DNS_ZONE_ID`) o en un
  archivo `.env` no versionado, que `.gitignore` ya excluye.
- Usa ejemplos solo con placeholders (`.env.example`) en plantillas y docs.
- El valor TXT de propiedad es publico por diseno; el archivo de estado local
  (`.ag/domains.json`) es estado del entorno, no un almacen de secretos. No
  pongas credenciales en el y mantenlo fuera del control de versiones si
  contiene datos especificos del entorno.
- Prefiere el flujo nativo: `attach`, `verify`, `diagnose` y `detach` no
  requieren credenciales. La automatizacion de proveedor queda tras una
  feature de Cargo opt-in.
- Manten privados los hostnames privados: sin prueba TXT publica, sin
  certificado publico y sin registro DNS publico.
- No trates un enlace comodin como una barrera de seguridad: hay un defecto
  de limite de etiqueta en la coincidencia SNI/ruta bajo auditoria en la
  ola 8. Prefiere hostnames exactos hasta corregirlo.
- Las tumbas de desadjunto previenen el takeover de subdominios; no acortes
  el valor por defecto sin una razon documentada.
