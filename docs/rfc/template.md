# RFC-XXXX - Titulo corto

- Estado: borrador
- Autor: Nombre Apellido (sin atribuciones a herramientas IA)
- Fecha de borrador: YYYY-MM-DD
- Fase objetivo: Fase N
- Modulos o crates afectados: lista
- RFC predecesora: ninguna o RFC-YYYY
- Periodo de comentarios: mininimo siete dias calendario

## 1. Motivacion

Por que esta decision es necesaria ahora. Que problema concreto del
proyecto resuelve. Que pasa si no se toma.

## 2. Problema

Definicion clara del problema. Datos cuantitativos cuando sea posible.
Referencias a issues, benchmarks, reportes de la comunidad, RFC
previas.

## 3. Alternativas consideradas

Enumeracion de opciones realistas, incluyendo la opcion de no hacer
nada. Para cada alternativa: ventajas, desventajas y por que no se
elige.

## 4. Diseno propuesto

Descripcion tecnica detallada de la decision. Incluya:

- Cambios en interfaces publicas, si hay.
- Cambios en dependencias.
- Cambios en CI o tooling.
- Cambios en documentacion maestra, si hay.
- Cambios en el DSL, si hay.
- Diagramas relevantes en `docs/diagrams/`.

## 5. Plan de implementacion

Lista de pull requests previstas para implementar la RFC. Indique
fases y dependencias entre PRs.

## 6. Riesgos

Riesgos tecnicos, de adopcion, de mantenimiento, de seguridad. Para
cada riesgo: probabilidad, impacto y mitigacion propuesta.

## 7. Impacto

- Sobre el alcance del producto.
- Sobre el cronograma del roadmap.
- Sobre la complejidad operacional.
- Sobre las APIs publicas.
- Sobre la documentacion existente.

## 8. Rollback

Como se revierte esta decision si resulta incorrecta. Que datos o
metricas indicarian que es momento de hacer rollback.

## 9. Decision

A completar tras el periodo de comentarios.

- Decisor: BDFL o comite tecnico.
- Fecha de decision: YYYY-MM-DD.
- Resultado: aceptada, rechazada o diferida.
- Justificacion breve.

## 10. Referencias

Enlaces a issues, discusiones, ADRs relacionados, capitulos del
maestro de arquitectura.
